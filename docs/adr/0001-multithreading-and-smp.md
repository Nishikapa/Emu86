# ADR-0001: 内部処理のマルチスレッド化とゲスト SMP(マルチコア/マルチ CPU)対応

- 状態: **保留(Deferred)** — 2026-10-12、第 1 ラウンドの質問提示後に利用者が「マルチ CPU・マルチコアのサポートは一旦保留」と決定。再開時は下記「未決の質問」から再開する。
- 日付: 2026-10-12
- 関連: [用語集](../glossary.md)

## 背景(コードから確定している事実)

Emu86 は現在、単一の仮想 CPU を単一のホストスレッドで逐次実行するインタプリタである。

| 観点 | 現状 | 根拠 |
|------|------|------|
| 実行ループ | `EmulationRunner.Run` が「スケジューラ・vCPU 実行・割り込み配送・デバイスポンプ・スナップショット」を 1 関数で兼ねる | `EmulationRunner.cs` |
| ゲスト時刻 | 実行済み命令数(100 万命令 = 1 秒)。TSC・ACPI PM タイマ・IRQ0 周期(1 万命令)がすべてこれに従う | `env.Tsc = count`、`AcpiPmDevice.Timer(tsc)` |
| 割り込みコントローラ | 8259 PIC のみ。Local APIC / I/O APIC は存在せず、CPUID でも APIC ビットを伏せている | `Cpuid_0FA2`(`d = 0x00008179`) |
| MMIO | 未実装。RAM 外は「読み 0xFF・書き無視」。LAPIC(0xFEE00000)/IOAPIC(0xFEC00000) を置く仕組みがない | `Environment.cs` の EnvWriteByte 付近コメント |
| CPU 固有状態の置き場所 | ページング状態と TLB(`Paging`: Enabled/Pae/WriteProtect/Cr3Base)、TSC、MSR、DR0-7 が **環境(EmuEnvironment)側** にある。実機ではいずれも CPU ごとの状態 | `Paging.cs`、`Environment.cs` の `EmuEnvironment` |
| アトミック性 | LOCK プレフィックスは無視(「単一 CPU なので」)。XCHG/CMPXCHG/XADD/CMPXCHG8B は通常の読み書きで実装。32 ビット書き込みは 1 バイトずつ 4 回の store | `FastCore.cs:38`、`EnvWriteDword` |
| HLT | NOP(待たずに次命令へ進む) | `Hlt_F4`、`FastCore.cs:453` |
| スナップショット | CPU は 1 個固定(v10) | `SnapshotStore.cs`、`CPU.Snapshot.cs` |
| 既存のスレッド | UI スレッド(VgaWindow、VRAM を無ロックで読む)、シリアルのパイプ送受信タスク、`EmulationControl` による中断/再開 | `Program.Runner.cs:126`、`SerialPort.cs` |
| 検証手法 | 命令トレースの Unicorn との完全一致、スナップショットからの再現実行。**決定論に強く依存** | `docs/boot-progress.md`、`tools/win-debug/` |
| ゲスト | Windows XP(halacpi.dll = ACPI **単一** プロセッサ HAL)、Debian 686-pae | メモリノート、boot-progress |

## 問題の分解

利用者の問いは 2 つの独立した問題を含む。

1. **ホスト側のマルチスレッド化** — エミュレータの処理を複数のホストスレッドに分ける。
2. **ゲスト側の SMP** — ゲスト OS から 2 個以上の CPU が見える。

(2) は (1) を必要としない(1 ホストスレッドで n 個の vCPU を時分割する方式がある)。
(1) は (2) がなくても可能だが、単一 vCPU のインタプリタをスレッド分割しても速くはならない
(命令の逐次依存のため)。したがって「速くしたい」が動機なら、スレッドではなく動的変換(JIT)が手段になる。

## 選択肢(暫定)

### A. 1 ホストスレッドで n vCPU を時分割(決定論的 SMP)
- 実行ループが vCPU[0..n-1] を一定量子(例: IrqPeriod と同じ 1 万命令、あるいはより細かく)で切り替える。
- ロック不要。既存の命令数クロック・トレース・スナップショット・Unicorn 照合がそのまま成り立つ。
- LOCK は現状どおり無視して正しい(切り替え境界が命令境界なので RMW は分断されない)。
- 性能はコア数で割られる(ゲストの総命令レートは変わらない)。
- APIC / MP テーブル / INIT-SIPI / HLT=待機 / CPU 固有状態の分離は必要(SMP の本体)。

### B. vCPU ごとに 1 ホストスレッド(並列 SMP)
- A の要件に加えて: 共有メモリの可視性、32 ビット store の分断対策、LOCK 付き RMW の実装
  (アラインされていれば `Interlocked`、またがる場合はグローバルロック)、デバイス状態の排他、
  TLB の CPU 分離(CR3 変更・INVLPG の他 CPU への TLB シュートダウンは IPI 経由でゲストが行う)。
- ゲスト時刻の基準が必要(各 vCPU の命令数は揃わない)。候補: ホスト単調時計、BSP の命令数、
  全 vCPU の合計/最大、専用のタイマスレッド。
- 決定論を失う。再現実行・トレース照合は「1 スレッドモードに落として再現」が必要になる。

### C. デバイス/表示/ディスクだけを別スレッドに出す(ゲストは単一 CPU のまま)
- 既に一部実施済み(表示・シリアル)。ATA 読み取りやスナップショット保存の非同期化は可能。
- ゲスト SMP には寄与しない。

## 共通して必要になるもの(A/B どちらでも)

- CPU 固有状態の `CPU` クラスへの移動: ページング状態・TLB・TSC・MSR・DR。
- MMIO の仕組み(ページ単位で物理ページを「デバイス」に振り分ける。TLB の物理ページ値に
  特別値を使えばホットパスの追加コストは小さい)。
- Local APIC(ID/SVR/ICR/LVT/タイマ/EOI/TPR)と I/O APIC(リダイレクションテーブル)。
  SeaBIOS は CPUID.1:EDX.APIC=1 なら INIT-SIPI をブロードキャストして AP を数え、MADT/MP テーブルを自前で出す。
- AP の初期状態(INIT 後 wait-for-SIPI、SIPI で `VV00:0000` のリアルモードから開始)。
- HLT を「割り込みまで待つ」に変更(SMP ではアイドル CPU が HLT で止まる前提)。
- CPUID の報告(APIC ビット、リーフ 1 の論理プロセッサ数/初期 APIC ID、必要なら リーフ 4)。
- スナップショット v11(CPU 個数 + 各 CPU + LAPIC 状態)。
- `EmulationControl`/`RegisterDialog`/`BootAutomation`/`RunDiagnostics` の複数 CPU 対応。
- ゲスト OS 側: XP は halmacpi.dll(ACPI マルチプロセッサ HAL)+ ntkrnlmp.exe が必要。
  現在のイメージは halacpi.dll(単一プロセッサ)。Linux(686-pae)は MADT があれば SMP 起動する。

## 未決の質問(第 1 ラウンド)

利用者への質問は本 ADR の末尾に回答とともに追記する。

1. 目的は「ゲストから複数 CPU が見える」ことか、「ホストの複数コアで速くする」ことか、両方か。
2. 最初に SMP 起動させたいゲストはどれか(XP / Debian / 自作テストコード)。XP の場合、HAL 差し替えをどう扱うか。
3. 決定論(トレース照合・再現実行)をどこまで守るか。「1 スレッド時分割モードを常備し、並列モードは任意」で良いか。
4. ゲスト時刻の基準をどうするか(命令数のまま vs ホスト時計)。
5. APIC/IOAPIC/MMIO を実装する覚悟があるか(SMP の必須条件であり、現行の PIC 経路と並存させる必要がある)。
6. n の上限と既定値(2 固定か、`--cpus n` か)。

## 決定

ゲスト SMP(選択肢 A/B)の実装は **一旦保留** とする(2026-10-12)。
第 1 ラウンドの質問 1〜6 は未回答のまま残す。再開する場合は、まず質問 1(目的)と 3(決定論の扱い)に答えてから選択肢を絞る。

本 ADR の「背景」表は、再開時に前提が変わっていないかを確認するチェックリストとして使う
(特に: CPU 固有状態の置き場所、MMIO の有無、LOCK/HLT の扱い、スナップショット版数)。

## 結果

- 現行コードは単一 vCPU・単一実行スレッドのまま。`LOCK` 無視・`HLT`=NOP・CPU 固有状態の環境側配置はそのまま許容する。
- 今後、CPU 固有状態(TLB/TSC/MSR/DR/ページング状態)に新たな項目を足すときは、将来の分離を妨げないよう `EmuEnvironment` ではなく `CPU` 側に置くことを推奨する(強制はしない)。
- 選択肢 C(デバイス・表示・ディスクのみ別スレッド)は本 ADR の対象外。必要になれば別 ADR とする。
