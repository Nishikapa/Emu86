# ADR-0004: ゲストの時計を「1 秒 = N 命令」で一貫させる(PIT を設定どおりに数える)

- 状態: **採用(Accepted)** — 2026-11-01。段階 1 と 3 を実装済み(下記「判断」「結果」)。段階 2 は必要になったら。
- 日付: 2026-10-31(提案)、2026-11-01(採用・段階 1 完了)
- 関連: `docs/boot-progress.md`「Debian: initramfs のシェルから先へ(2026-10-31)」、`EmulationRunner.cs`(タイマ IRQ と HLT)、
  `GuestClock.cs`、`PitDevice.cs`、`AcpiPmDevice.cs`、`CmosDevice.cs`、[ADR-0001](0001-multithreading-and-smp.md)(用語「ゲスト時刻」)

## 背景(提案時点のコードから確定していた事実)

ゲストが観測する時間はすべて「実行済み命令数」(`env.Tsc` = ランナーの count)から作っていたが、換算が装置ごとに違った。

| 時計 | 今の実装 | ゲストから見た速さ |
|------|------|------|
| タイマ IRQ(IRQ0) | `IrqPeriod = 10,000` 命令ごとに必ず立てる。PIT チャネル 0 に書かれた再装填値(周期)は見ない | HZ=100 の XP では 1 秒 = 100 万命令、HZ=250 の Linux では 1 秒 = 250 万命令 |
| PIT チャネル 0 の読み出し | ラッチのたびに 0x100 ずつ減らす代用値。再装填値・モードは保持しない | 時間と無関係 |
| PIT チャネル 2 | 書き込み完了で「武装」し、ポート 0x61 を 2 回読むと OUT を立てる(TSC 較正のウェイトを抜けさせる) | 時間と無関係 |
| ACPI PM タイマ(3.579545 MHz) | `tsc × 3,579,545 / 1,000,000` | 1 秒 = 100 万命令 |
| CMOS RTC | `tsc / 1,000,000` 秒 | 1 秒 = 100 万命令 |
| TSC(RDTSC) | 命令数そのもの | 較正結果しだい(Linux は PIT 較正で約 3.5 MHz と判定した) |
| HLT | 配送できる割り込みが無ければ次のイベント(IRQ0・サービス周期・保存・上限)まで count を進める | 時間 = 命令数 なので一貫 |

結果として、ゲストから見た CPU は 1〜3.5 MHz 相当になる。実行速度は 3,000 万〜1 億命令/秒なので、ゲスト時間は実時間の 10〜100 倍の
速さで進む。XP はこれでも GUI まで起動する(タイムアウトに寛容)が、Debian では次の形で現れた(`docs/boot-progress.md`):

- udevd がモジュール 1 個のロードに約 8,000 万命令 = ゲスト時間で 20 秒以上かかり、`soft lockup - CPU#0 stuck for 22s!` が出る。
- initramfs の root 待ち(30 秒 = 3,000 万〜1 億命令)が、udev が `ata_piix` をロードする前に尽きて「root が見つからない」になる。
  手で `modprobe ata_piix; modprobe sd_mod; exit` と打てば root はマウントされ systemd が起動する。
- systemd のサービス起動タイムアウト(90 秒 = 1〜3 億命令)で udev と journald が失敗を繰り返す。
- X.509 証明書のロードが `-110`(ETIMEDOUT)で失敗する。

また Linux ではタイマ IRQ(2.5M 命令/秒)と PM タイマ(1M 命令/秒)の速さが食い違うので、jiffies と clocksource の時間がずれる。

## 問い

「ゲストの時計を一貫させて、時間に依存する処理(タイムアウト、較正、スケジューリング)が実機に近い命令数で動くようにできるか。
決定性(同じ入力なら同じ実行。スナップショット・golden・状態比較の基盤)は保つ」。

## 選択肢

### A. 「1 秒 = N 命令」を 1 か所で決め、すべての時計をそこから導く(推奨)

- `InstructionsPerSecond`(IPS)を環境の定数(既定値)とオプション(`--ips`)で持つ。
- PIT チャネル 0 を本物として数える: 再装填値とモードを保持し、count = 再装填値 − ((tsc − 設定時刻) × 1,193,182 / IPS) mod 再装填値、
  IRQ0 の周期 = 再装填値 × IPS / 1,193,182 命令(0 = 65536 → BIOS の 18.2 Hz、XP の 10 ms、Linux の 4 ms がそのまま出る)。
  ラッチ読み出しは本物の count。チャネル 2 も同じ数え方で OUT を出す(TSC 較正のループは時間で自然に終わる)。
- PM タイマ = tsc × 3,579,545 / IPS、RTC = tsc / IPS 秒、TSC = 命令数のまま(較正すれば IPS になる)。
- ランナーの `IrqPeriod` は PIT が決める。キーボードの Pump などの「サービス周期」は時間ではないので固定のまま(1 万命令)。
- HLT の待ち、スナップショットの間隔、予算の計算は命令数のままでよい(時間 = 命令数の関係は保つ)。
- 既定の IPS: **5,000 万**(翻訳ありの実行速度 3,000 万〜1 億命令/秒に近く、ゲスト時間がおおむね実時間で進む。XP の 65 億命令の起動は
  130 秒相当)。`--ips` で変えられる(遅い機械で実時間に合わせる、タイムアウトを圧縮して速く起動を試す、など)。

利点: 時間に依存する処理が実機に近い命令数で動く(Debian の udev・systemd、X.509)。タイマ IRQ が 1/50 に減って Step の境界も減る。
PIT の読み出しが本物になり、PIT を使った遅延ループ(SeaBIOS、NTLDR)が正しい時間で回る。

欠点・費用: 挙動が変わるので、golden(タイマ IRQ の位置)と XP 65 億命令の状態基準を採り直す。PIT の状態(再装填値・モード・設定時刻)を
スナップショットに足す(v11、v10 以前の読み込みは既定値)。XP がタイムアウト前提で動いていた箇所(ATA、KD のタイムアウトは
「100 万命令 = 1 秒」と README に書いてある)の確認が要る。

### B. 命令数の時計のまま、換算だけ揃える(IPS = 100 万)

PM タイマ・RTC・PIT の周期を「1 秒 = 100 万命令」で揃える(PIT を設定どおりに数えるのは A と同じ)。

- 利点: 変更が小さく、XP の既存の時間感覚(100 万命令 = 1 秒)を保つ。
- 欠点: ゲストから見た CPU は 1 MHz のままで、Debian の問題(モジュール 1 個 = 80 秒、systemd の 90 秒)は解けない。

### C. ホストの実時間を時計にする

- 決定性を失う(同じ実行が再現しない: スナップショット比較・golden・状態の二分探索が使えなくなる)。採らない。

## 結果(段階 1、2026-11-01)

実装(`GuestClock.cs`、`PitDevice.cs` の書き直し、`AcpiPmDevice.cs`、`CmosDevice.cs`、`EmulationRunner.cs`、`RunOptions.cs --ips`、スナップショット v11):

- `GuestClock`: `InstructionsPerSecond`(既定 5,000 万、`--ips`)と、命令数 ⇄ ティック(1,193,182 Hz / 3,579,545 Hz)・秒の換算。秒の部分と端数を分けて
  計算するので、長い走行でも溢れない。環境ごとに持ち、スナップショットに保存する(v10 以前の読み込みは既定値)。
- PIT: チャネル 0/2 の再装填値・モード・アクセス・開始時刻を保持し、カウントは「開始からの経過ティック」から計算するだけ(周期ごとの更新はしない)。
  モード 0/1/4/5 は 1 回だけ(終端後は IRQ0 を立てず、`NextTimerIrq` は `long.MaxValue`)、2/3 は周期的(3 は 2 ずつ)。ラッチ、リードバック(状態バイト)、
  ポート 0x61 のゲート・OUT・リフレッシュビット(18 ティックごと)。チャネル 0 の設定が変わると `Changed` が立ち、ランナーが次の IRQ0 の時刻を取り直す。
- ランナー: 旧 `IrqPeriod`(1 万命令ごとの IRQ0)は廃止。IRQ0 の時刻は PIT が決め、キーボードの Pump などは `ServicePeriod`(1 万命令)で回る。
  HLT の待ちは次の IRQ0・サービス周期・保存・上限のうち最も近いものまで(変更なし)。
- テスト: `devices` に PIT の数え方(モード 2 のラッチ値、1 回だけのモードの IRQ0、チャネル 2 の OUT とリフレッシュ)を追加。golden・`runner/compare`・
  `completion` の環境は「IPS = 1,193,182(1 ティック = 1 命令)、PIT の再装填値 10,000」に設定し、IRQ0 の位置を従来と同じに保ったので命令数と
  トレースは不変。状態のハッシュだけを採り直した(スナップショットの項目が増えた分)。

検証(翻訳あり、冷起動、`--rtc 2026-11-01T00:00:00`):

| ゲスト | 上限 | 実時間 | 結果 |
|------|------|------|------|
| XP(sample.vhd) | 300 億命令 | 352 秒 | ミニセットアップの GUI(使用許諾契約のページ)に到達。HLT で飛ばしたアイドルが 160 億命令(53.5%)で、IRQ0 が 100 Hz(1 万命令ごと → 50 万命令ごと)になった分だけアイドル待ちが長く数えられる |
| Debian(sample.vhdx) | 400 億命令 | 975 秒 | 120 億命令(ゲスト時間 240 秒)で udev が自分でモジュールをロードし(`bochs_drm` は「less than 4 MB video memory, ignoring device」で辞退)、initramfs が root を見つけて `/dev/sda1: clean`。140 億命令で systemd のサービスが `[ OK ]` で進み(Local File Systems、swap、AppArmor、Plymouth Boot Screen、Network Time Synchronization、Raise network interfaces)、タイムアウトは出ない |

段階 1 の完了条件は両方とも満たした。Debian の次のブロッカー(`docs/boot-progress.md`): 「Show Plymouth Boot Screen」の後、160 億命令以降は文字 VRAM が空で
画面が真っ黒(カーソルだけ)、CPU はユーザーモードで忙しいまま(アイドル 0.5〜3%)。400 億命令の時点で Enter を送っても 20 秒(10 億命令)では何も出ない。

ゲストの時計に残る既知の単純化: RTC の周期割り込み(IRQ8)は無い(段階 2)。VGA の垂直帰線の擬似は `Tsc` の下位ビットのままで `GuestClock` を使っていない。

段階 3(文書)は同時に行った: README(PIT の行、「ゲストの時刻」、KD のタイムアウト、`--ips`)、`docs/glossary.md`、テストの README。
